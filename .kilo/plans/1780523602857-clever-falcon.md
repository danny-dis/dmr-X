# Plan: DMR-X MCP Router as a Plugin Architecture

## Goal
Enable DMR-X to function as an **MCP router** through a plug-in architecture that requires **zero modifications** to the existing codebase (`router`, `adapters`, `gateway`, `core`, `utils`, etc.). The MCP capability should be loadable, unloadable, and composable at the process boundary.

## Research Findings

### Current State
| Component | Role | MCP Awareness |
|-----------|------|---------------|
| `services/mcp-server/` | Standalone MCP server (stdio/SSE/HTTP) | Creates its OWN `Router` + `AdapterRegistry` — no shared state with gateway |
| `apps/gateway/` | OpenAI-compatible HTTP API | Built-in `registerToolHandler` registry is the closest existing plugin hook; gateway also exposes `registerToolHandler` as a Fastify decorator |
| `services/router/` | Routing engine | Accepts `AdapterExecutor` via `setAdapterExecutor()` — the natural plugin injection boundary |
| `services/adapters/` | Provider adapters | `AdapterRegistry.register()` — already supports dynamic registration |
| `packages/core/` | Shared types | Defines `UnifiedRequest`, `UnifiedResponse`, `ProviderPreferences`, `StreamChunk` — used by both gateway and MCP server |
| `packages/utils/` | Utilities | Exports `logger`, `CircuitBreaker`, HTTP helpers, tool orchestration primitives |

### Key Observation: Existing Plugin-Like Pattern
The gateway's `services/mcp-server` already operates as a separate process with its own Router. The same `Router.route()` method, `AdapterRegistry`, and `UnifiedRequest/Response` types are shared, but the MCP server duplicates their instantiation.

### Constraint: Zero Regression, Zero Existing-Code Modification
No changes to any existing file outside of:
- New files in `packages/plugin-loader/`
- New files in `services/mcp-server/src/plugin-entry.ts`
- Additive exports only in existing `services/mcp-server/src/`

## Architecture Strategy

### Design Patterns Applied

| Pattern | Where Used | Rationale |
|---------|-----------|-----------|
| **Dependency Inversion** | MCP plugin depends on `Router`/`AdapterRegistry` interfaces, not their concrete instantiation | Enables swapping implementations |
| **Inversion of Control** | Plugin receives its dependencies from a loader, not constructor-injected | Allows zero-modification composition |
| **Observer/Registry** | `AdapterRegistry.register()` is already an open registration point | Plugins can register new adapters dynamically |
| **Strategy** | `Router.setAdapterExecutor()` accepts any `AdapterExecutor` | Plugin can provide alternate execution strategies |

### High-Level Flow

```
                    ┌───────────────────────────────────────────┐
                    │      Plugin Loader (NEW — zero-impact)    │
                    │                                           │
                    │  Discovers plugins → injects dependencies  │
                    │  → calls plugin.init(router, adapters, cfg)│
                    └────────────┬──────────────────────────────┘
                                 │ injects existing instances
                                 ▼
 ┌────────────────────────────────────────────────────────────────┐
 │                    DMR-X Gateway (UNCHANGED)                   │
 │                                                                │
 │   ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐  │
 │   │    Router    │  │ AdapterReg   │  │ ToolHandlerRegistry│ │
 │   │   (existing) │  │  (existing)  │  │  (existing)       │  │
 │   └──────────────┘  └──────────────┘  └──────────────────┘  │
 └────────────────────────────────────────────────────────────────┘

                    ┌───────────────────────────────────────────┐
                    │     MCP Plugin (NEW — wraps + extends)    │
                    │                                           │
                    │   services/mcp-server/src/plugin-entry.ts  │
                    │                                           │
                    │  init(router, adapters, stateStore) →      │
                    │  - Registers MCP tool handlers            │
                    │  - Creates MCP server (stdio/SSE/HTTP)     │
                    │  - Maps MCP params → Router.route()        │
                    │  - Returns context management, streaming   │
                    └───────────────────────────────────────────┘
```

### Why This Is Zero-Modification

1. **Gateway is untouched** — The loader is an external process that imports gateway components and the MCP plugin, composes them, then runs.
2. **Router is untouched** — Plugin calls `router.route()`; router knows nothing about MCP.
3. **Adapters untouched** — Plugin calls `adapterRegistry.get()` and `adapterRegistry.register()`.
4. **Core types untouched** — Plugin uses `UnifiedRequest`, `Modality`, `ProviderPreferences` as-is.
5. **Existing MCP server continues working standalone** — `services/mcp-server/src/index.ts` is preserved verbatim. The plugin entry is a NEW file, not a modification to existing logic.

## Detailed File Specifications

### 1. `packages/plugin-loader/src/plugin.ts` — Plugin Contracts

```typescript
/**
 * Minimal plugin contracts for DMR-X.
 *
 * These interfaces live in a dedicated package so plugins can depend on
 * the contract without circular-importing any DMR-X implementation package.
 */

export interface PluginDependencies {
  /** DMR-X routing engine — plugins call route() to dispatch requests */
  router: {
    route(request: UnifiedRequest, options: ClassifyOptions): Promise<RouteResult>;
    setCandidates(candidates: CandidateSet): void;
    setAdapterExecutor(executor: AdapterExecutor): void;
    getCandidateCount(): number;
  };
  /** Adapter registry — plugins register adapters and look them up */
  adapterRegistry: {
    register(adapter: ProviderAdapter): void;
    get(providerId: string): ProviderAdapter | undefined;
    list(): string[];
    initialize(providerId: string, config: ProviderConfig): Promise<void>;
  };
  /** Shared state bag — plugins can store/read persist data */
  stateStore: StateStore;
  /** Node-style logger */
  logger: Logger;
  /** Environment/config accessor */
  config: Record<string, string | undefined>;
}

export interface PluginManifest {
  id: string;
  name: string;
  version: string;
  description: string;
  transport: PluginTransportConfig;
  tools?: PluginToolDefinition[];
  permissions?: PluginPermissions;
}

export interface PluginTransportConfig {
  type: 'stdio' | 'sse' | 'http' | 'embedded';
  http?: { port: number; host: string };
}

export interface PluginToolDefinition {
  name: string;
  description: string;
  inputSchema: SchemaLike;              // Zod-compatible
}

export interface PluginPermissions {
  accessModalities: Modality[];
  canRegisterAdapters: boolean;
  canReadCandidates: boolean;
  canAccessDatabase: boolean;
}

export interface Plugin {
  /** Unique plugin ID */
  readonly id: string;
  /** Load dependencies injected by the loader */
  init(deps: PluginDependencies): Promise<void> | void;
  /** Start plugin (e.g., open SSE port, begin listening on stdio) */
  start?(): Promise<void> | void;
  /** Stop plugin and release resources */
  stop?(): Promise<void> | void;
}

export interface StateStore {
  get<T>(key: string): Promise<T | undefined>;
  set<T>(key: string, value: T, ttlSeconds?: number): Promise<void>;
  delete(key: string): Promise<void>;
  keys(prefix?: string): Promise<string[]>;
}
```

### 2. `packages/plugin-loader/src/plugin-loader.ts` — Loader Core

```typescript
/**
 * Plugin Loader — discovers, loads, and composes plugins into DMR-X.
 *
 * Key principle: the loader imports plugins dynamically; plugins never
 * statically import the gateway or router. Dependency injection is the
 * only coupling mechanism.
 */

export interface PluginLoaderConfig {
  pluginsDir?: string;                  // e.g. "services/plugins"
  enabledPlugins?: string[];            // explicit allow-list
  pluginOverrides?: Record<string, { http?: { port?: number } }>;
}

export class PluginLoader {
  private plugins: Map<string, Plugin> = new Map();
  private manifests: Map<string, PluginManifest> = new Map();

  async load(config?: PluginLoaderConfig): Promise<PluginManifest[]> {
    const pluginDirs = this.discoverPlugins(config?.pluginsDir);
    const manifests: PluginManifest[] = [];

    for (const pluginDir of pluginDirs) {
      const manifest = this.loadManifest(pluginDir);
      if (config?.enabledPlugins && !config.enabledPlugins.includes(manifest.id)) {
        continue;
      }
      this.manifests.set(manifest.id, manifest);

      const pluginModule = await this.dynamicImport(pluginDir, manifest.id);
      const plugin: Plugin = pluginModule.default ?? pluginModule;

      await plugin.init({ router: wrapRouter(...), adapterRegistry: wrapRegistry(...), ... });
      this.plugins.set(manifest.id, plugin);
      manifests.push(manifest);

      if (plugin.start) await plugin.start();
    }

    return manifests;
  }

  async stopAll(): Promise<void> {
    for (const [id, plugin] of this.plugins) {
      if (plugin.stop) await plugin.stop();
    }
  }

  private async dynamicImport(pluginDir: string, pluginId: string): Promise<unknown> {
    const entry = path.join(pluginDir, pluginId, 'index.ts');
    // Uses dynamic import() — no static coupling
    return import(entry);
  }
}
```

The loader wraps the gateway's `Router` and `AdapterRegistry` to satisfy the `PluginDependencies` interface without exposing internal methods.

### 4. `services/plugin-loader-bootstrap/src/bootstrap.ts` — Runnable Bootstrap

```typescript
/**
 * Zero-modification bootstrap: composes gateway + plugins into a running system.
 *
 * Run with:
 *   bun services/plugin-loader-bootstrap/src/bootstrap.ts
 *   bun services/plugin-loader-bootstrap/src/bootstrap.ts --plugin mcp-server --transport sse --port 3100
 */

import { createServer } from '@dmr-x/gateway/src/server.js';     // gateway's createServer()
import { PluginLoader } from '@dmr-x/plugin-loader';
import { createMCPPlugin } from '@dmr-x/mcp-server/src/plugin-entry.js';

async function main() {
  const args = parseArgs(Deno.args);

  // 1. Start the gateway (unchanged — no new deps)
  const gateway = await createServer();

  // 2. Extract gateway internals to inject into plugins
  const deps: PluginDependencies = {
    router: gateway.router,                                        // Fastify-decorated
    adapterRegistry: gateway.adapterRegistry,
    stateStore: createInMemoryStateStore(),
    logger: console,
    config: { ...process.env },
  };

  // 3. Load plugins
  const loader = new PluginLoader();
  await loader.load({
    enabledPlugins: args.plugins ?? ['mcp-server'],
  });

  await gateway.listen({ port: parseInt(args.port ?? '3000'), host: '0.0.0.0' });
}

main();
```

## Integration Paths (Three Deployment Modes)

### Mode A: Standalone MCP Server (CURRENT — preserved)
```
Client → services/mcp-server (index.ts)
                    │
                    ▼
            Own Router + Own AdapterRegistry
```
No changes. Existing `npm run start:dev` for MCP server still works.

### Mode B: Embedded Plugin in Gateway (NEW)
```
Client → Gateway routes /v1/** → existing OpenAI-compatible API
Client → MCP Plugin (via stdio/SSE) → shared Router + AdapterRegistry
```
The bootstrap (`services/plugin-loader-bootstrap/`) initializes gateway first, then loads MCP plugin, both running in the same Node.js process sharing the same Router and candidates.

### Mode C: Sidecar Process (NEW)
```
MCP Client                         Gateway
    │                                  │
    │  stdio / SSE / HTTP              │  /v1/chat/completions, etc.
    │                                  │
    ▼                                  ▼
  MCP Plugin                      Gateway Router
  (plugin-entry.ts)                    │
    │                                  │
    └──── both hit same DB ────────────┘
```
MCP server runs its own process but connects to the gateway via exposed HTTP endpoints for routing decisions, candidate queries, and adapter initialization. **Zero file sharing** between the two processes.

## Risks and Mitigations

| Risk | Severity | Mitigation |
|------|----------|-----------|
| Plugin loader introduces circular imports | HIGH | `plugin-loader` depends on NOTHING from DMR-X (pure interface package); it uses dynamic `import()` to load plugins |
| Shared Router state concurrency | MEDIUM | Gateway is single-process single-threaded (Node.js + Fastify); plugins run in same event loop. No concurrent mutation of Router state. |
| Adapter double-registration | LOW | Plugin checks `adapterRegistry.get()` before `register()`. Loader ensures init order. |
| State store bloat | LOW | In-memory store with optional TTL; long-running sessions should persist to DB via existing gateway routes. |
| Plugin crash brings down gateway | MEDIUM | Each plugin init/start is wrapped in try/catch. Faulty plugin is skipped, not propagated. |
| Type safety through dynamic imports | MEDIUM | `Plugin` interface enforces contract at compile time; dynamic imports use `unknown` with runtime instanceof checks. |
